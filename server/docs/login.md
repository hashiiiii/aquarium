# ゲームアプリ認証設計ガイド

1ユーザー1端末・自動リフレッシュ方式によるモバイルゲームアプリの認証・認可フロー設計。

---

## 1. 基本構成

### 1.1 識別子の役割

| 識別子 | 役割 | 備考 |
|--------|------|------|
| **Platform Acount ID** (Apple / Google) | ユーザー本人の不変な証明 | アンインストール・機種変更時のデータ復旧用 |
| **Device ID** (UUID) | 現在操作している端末の識別 | 初回起動時に生成し、セキュアな領域に保存 |
| **Access Token** (JWT) | API実行時の通行証 | ペイロードに `user_id` と `device_id` を含む |

#### Device ID の保存先

- **iOS**: Keychain
- **Android**: EncryptedSharedPreferences

### 1.2 ストレージ構成

| ストレージ | 役割 |
|-----------|------|
| **MySQL (Writer)** | ユーザーマスターデータの永続化（`current_device_id` を含む） |
| **MySQL (Reader)** | 参照用レプリカ |
| **Redis** | User モデルのキャッシュ。API実行時の高速な認可チェックに使用 |

## 2. 認証フロー

### 2.1 ログイン・再ログイン (`/login`)

トークン初回発行、および期限切れ時の復旧に使用。

#### リクエスト

```json
{
  "device_id": "uuid",       // 必須
  "platform_id": "string",   // 任意（Apple/Google連携後に送信）
  "transfer_id": "string"    // 任意（アカウント移行時のみ）
}
```

#### ユーザー特定ロジック（優先順位順）

```
1. transfer_id != nil
   └─→ transfer_id から User を検索
       └─→ 見つかった → device_id を UPDATE, transfer_id を NULL にクリア
       └─→ 見つからない → エラー

2. platform_id != nil
   └─→ platform_id から User を検索
       └─→ 見つかった → device_id が異なれば UPDATE
       └─→ 見つからない → 3 へ fallthrough

3. device_id != nil
   └─→ device_id から User を検索
       └─→ 見つかった → その User を使用
       └─→ 見つからない → 新規 User 作成
```

> **transfer_id の用途**: Platform 未連携 （`device_id` のみ） のユーザーが機種変更する際のセーフティネット。Platform 連携済みなら `platform_id` で復旧できるため不要。

#### ユースケース別の動作

| ケース | 送信パラメータ | 動作 |
|--------|---------------|------|
| 初回起動 | `device_id` のみ | 新規ユーザー作成 |
| 通常ログイン | `device_id` のみ | 既存ユーザーでログイン |
| プラットフォーム連携後 | `device_id` + `platform_id` | platform_id で特定、device_id を更新 |
| 機種変更（連携済み） | 新 `device_id` + `platform_id` | 既存ユーザーの device_id を新端末に更新 |
| 機種変更（未連携） | 新 `device_id` + `transfer_id` | transfer_id で特定、device_id を更新、transfer_id をクリア |

> **Note**: Platform 連携済みなら `platform_id` で復旧できるため `transfer_id` は不要。`transfer_id` は Platform 未連携ユーザー専用の機種変更手段。

#### シーケンス

```
Client                          Server
  |                               |
  |-- POST /login --------------->|
  |   { device_id, platform_id?,  |
  |     transfer_id? }            |
  |                               |-- ユーザー特定ロジック実行
  |                               |-- current_device_id を更新
  |                               |-- Redis キャッシュを 更新 / 削除
  |                               |
  |<-- JWT (user_id, device_id) --|
```

> **Note**: `platform_id` でユーザーを特定した際に `device_id` を更新することで、旧端末は次回 API アクセス時に `401` となり自動的にログアウトされる。

### 2.2 汎用 API 実行 (`/foo` 等)

```
Client                          Server
  |                               |
  |-- GET /foo ------------------>|
  |   Authorization: Bearer JWT   |
  |                               |
  |                               |-- Step 1: JWT 署名検証（メモリ内で完結）
  |                               |-- Step 2: Redis から User キャッシュ取得
  |                               |           （なければ MySQL Writer から再構築）
  |                               |-- Step 3: User の device_id と JWT の device_id を比較
  |                               |
  |<-- 200 OK / 401 Unauthorized -|
```

**認可結果**:
- 一致 → 処理続行
- 不一致 → `401 Unauthorized`

### 2.3 クライアント側の自動リトライ

HTTP クライアントの Interceptor で以下を実装:

1. `401` を検知
2. 自動的に `/login` を叩いてトークン更新
3. 元の API を再試行
4. `/login` も失敗（`403` 等）→ 他端末への移行済みとみなしタイトル画面へ

## 3. 設計判断の経緯

| 検討案 | 採否 | 理由 |
|--------|------|------|
| JWT署名検証のみ | 不採用 | 端末Bログイン後も、端末AのJWTが切れるまで共存を許してしまう |
| 1端末制限の撤廃 | 不採用 | アカウント共有・チート（24時間稼働）のリスク、データ不整合 |
| **プランA（毎回Redis参照）** | **採用** | Redis は十分高速。シンプルな実装で「即座に他端末をキック」が可能 |

## 4. エッジケースと対策

### 4.1 アンインストール対策

OS標準のID（Sign-in with Apple/Google）をバックアップキーとして使用。
UUIDが消失しても `/login` 時に元の `user_id` を特定し、新しいUUIDを紐付け直してサイレント復旧。

### 4.2 レプリケーション遅延への対応

`/login` 直後のAPI実行を考慮し、Redis キャッシュがない場合は **Reader ではなく Writer** を参照。

### 4.3 Redis 障害への対応

1. **フォールバック**: MySQL Writer を参照
2. **L1キャッシュ**: アプリサーバーのローカルメモリに数秒間だけ User 情報を保持（負荷軽減）

### 4.4 他端末ログイン（後勝ち）の挙動

1. 端末B がログイン → Redis の `device_id` が即座に書き換わる
2. 端末A の次のAPIリクエストで `401`
3. 端末A の `/login` が失敗 → タイトル画面へ

**結果**: 完全な「後勝ち」を保証

## 5. 技術的背景

### 5.1 認証と認可の境界

| 概念 | 目的 | タイミング | 本設計での位置づけ |
|------|------|-----------|-------------------|
| **認証** (Authentication) | 「誰であるか」を確認 | `/login` 実行時 | OS Social ID を検証しユーザーを特定 |
| **認可** (Authorization) | 「実行する権利があるか」を確認 | 各APIリクエスト時 | JWT署名検証 + Redis でのデバイスチェック |

### 5.2 JWT を採用する理由

セッションIDではなくJWTを使う理由:

#### 1. サーバーメモリでの一次切り分け

- JWT は自己署名されているため、DB/Redis アクセス前に偽造・期限切れを判定可能
- 不正リクエストをインフラ深層に到達させない → 攻撃耐性向上

#### 2. 水平スケール時の対応

API サーバーを複数台にスケールアウトしても、各サーバーが同じ秘密鍵を持っていれば JWT を検証できる。

```
[ロードバランサー]
       ↓
 ┌─────┼─────┐
API-1  API-2  API-3  ← 全サーバーが同じ秘密鍵を保持
```

鍵の配布は環境変数やシークレット管理（AWS Secrets Manager 等）で行う。

##### 署名方式

| 方式 | 署名 | 検証 | 用途 |
|------|------|------|------|
| **共通鍵 (HS256)** | 秘密鍵 | 同じ秘密鍵 | 単一サービス構成（本設計） |
| **公開鍵 (RS256)** | 秘密鍵 | 公開鍵 | JWT 発行と検証が別サービスの場合 |

本設計では API サーバーが JWT の発行・検証を両方行うため、**HS256（共通鍵方式）** を採用。
サーバー側はクライアントに JWT を渡す。クライアントはそのままサーバーに JWT を返す。サーバーは受け取った JWT と、その場でヘッダーとペイロードから署名を作成して、一致しているか検証する。
